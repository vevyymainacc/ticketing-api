This is a ticketing API i built across a day as a hobby, it's a small back-end service for booking event seats that wont oversell or accidentally books two seats at once, even if many try booking at the exact same time

I built this because i wanted to build a project to proove to myself that i can handle working with backend that actually can break on concurrency, anyone can write a booking endpoint that works for one person but i wanted to proove to myself that i can get past the hard question: "What if 200 book at once?"

I chose to use Rust because it's type system catches many concurrency mistakes before the code runs

It models events and individual seats, lets a client reserve a seat for an event over HTTP, guarantees a seat is booked for only one person (preventing 200 booking the same seat) and supports safe retries by an indempotency key (e.g. a network response that dropped wont buy 2 seats)

It works by using reserve_any_seat inside a single database transaction (all or nothing)

1. If a request carries 'Idempotency-Key' that was already booked under, it returns the original booking rather than making a new one making sure that if the first request suceeded while the response got lost client will retry instead of booking a second seat

2. it locks a free seat by running 'SELECT' & 'FOR UPDATE SKIP LOCKED' to grab the next available seat and lock it, 'FOR UPDATE' locking the row so others wont take it, 'SKIP LOCKED' meaning another request doesent queue behind a locked seat skipping to the next available one but if there is no seat to lock it assumes the event is sold out so it returns 409

3. it inserts the booking into the 'bookings' table, that table has a 'UNIQUE' constraint on the idempotency key so even if two identical requests both slip past step 1 at the exact same time only one of the inserts can actually win, the other one hits a unique violation error which it catches, rolls back and returns the booking that already won instead of erroring out, so a client can never end up with two seats

4. after the seat is locked and the booking is inserted it marks the seat as 'held' with an expiry time and then commits the transaction, only after that commit does any of this become real and visible to everyone else, and if any step along the way fails the whole transaction rolls back so it's like nothing ever happened, meaning you never get a half finished booking or a seat stuck as taken with no booking behind it

on top of those steps i set the transaction to run at 'READ COMMITTED' on purpose, the safety here comes from the row lock in step 2 and not from the isolation level so i didn't need anything stronger, a level like 'SERIALIZABLE' wouldn't make it any safer it would just make postgres abort some transactions with errors that i'd have to catch and retry

reserving a seat doesn't book it straight away anymore, it puts a temporary hold on it that expires after a couple of minutes, the idea is the same as a checkout timer, you hold a seat while you're paying and then you confirm it with 'POST /reservations/:idempotency_key/confirm' which flips it from held to booked, if you never confirm then the hold just expires, a background task runs every few seconds and sweeps any expired holds back to available so a seat is never stuck held forever, and because the seat picker only ever grabs available seats an expired hold becomes bookable again the moment it's swept

i also wanted it to hold up when things go wrong and not just on the happy path, so the 'Idempotency-Key' header is now required on a reservation, if you don't send one you get a 400, the reason it's required is that it's what makes a retry safe after a crash, if the server commits the booking but dies before the response reaches the client then the client just retries with the same key and gets the original booking back instead of a second seat, and to recover a response that got lost there's a 'GET /reservations/:idempotency_key' that returns the original booking or a 404 if there isn't one

it also sheds load instead of falling over, there's a cap on how many requests can be in flight at once and if it's already full the extra ones get a '503' with a 'Retry-After' header straight away instead of piling up in a queue that never drains, the database connection pool works the same way, if a request can't get a connection in time it gets a '503' too rather than hanging forever, and any single request that runs too long gets cut off with a '408' so one slow query can't hold a connection hostage

it also shuts down gracefully, when it gets a stop signal it stops accepting new requests, lets the ones already in flight finish and closes the database pool cleanly, so a deploy or restart doesn't drop requests mid way

i also added proper observability so i can actually see what it's doing under load instead of guessing, it exposes a 'GET /metrics' endpoint in prometheus format with the request rate, error rate and latency per endpoint plus how many requests are in flight right now, the logs are structured json and every request gets a request id that goes into its log line and comes back in an 'x-request-id' header so a single request can be traced end to end, and there's a prometheus and grafana setup in docker compose with a dashboard already wired up so you can watch the rate, latency and in flight panels live

the api itself is small, 'POST /events' creates an event with a number of seats, 'GET /events/:event_id' shows how many seats are available, held and booked, 'GET /health' is a basic liveness check, 'GET /ready' also checks that the database is reachable, 'POST /events/:event_id/reservations' puts a hold on a seat (you have to send an 'Idempotency-Key' header so a retry is safe), 'POST /reservations/:idempotency_key/confirm' turns that hold into a real booking, 'GET /reservations/:idempotency_key' looks up an existing reservation by its key so a client can get back a response it lost, and 'GET /metrics' exposes the prometheus metrics

it's built with Rust and Axum for the http layer, SQLx with PostgreSQL for the database, and Docker plus GitHub Actions for running it locally and for CI

for testing, the main test creates an event with 50 seats then fires 200 reservation attempts at the exact same time, it checks that exactly 50 succeed, 150 come back sold out and that no seat is ever booked twice, that last check is the real proof that the concurrency handling works, and CI runs it against a real postgres on every push. i also added tests for the idempotency side, one fires lots of requests with the same key at the same time and checks they all end up as a single booking and a single seat, a test for the hold flow that confirms a held seat actually becomes booked, a test that an expired hold gets swept back to available, and a separate test proves the load shedding by sending more requests than the limit and checking the extra ones come back as 503

i also load tested it properly with k6 rather than just firing requests by hand, i ran k6 as a container against the dockerized api and ramped up to 200 virtual users, on the sold out path it held around 5,500 requests a second with a p99 of about 38ms and zero errors, the load test also caught a real bug i wouldn't have found any other way, creating an event with 10,000 or more seats was failing because the seat labels used 'lpad' with a width of 4 and postgres truncates anything longer than the width, so seat 10000 and 10001 both came out as the same label and tripped the unique constraint, the little 50 seat test never went near that limit but load at scale did, i fixed the width and added a test so it can't come back

the more interesting find was that the booking write path was slow, like 1,240 bookings a second with a p95 of 121ms, i ran 'EXPLAIN ANALYZE' on the seat picking query and saw it was sorting every available seat by label on every booking just to pick one, that meant sorting up to 50,000 rows per request because my index was on '(event_id, status)' which doesn't include the label, so i switched to a partial index on '(event_id, label) where status = available' so postgres can walk the index in label order and grab the first free seat with no sort at all, that one query went from 22ms down to 0.077ms, the booking throughput more than doubled to around 2,800 a second and the p95 went from 121ms down to 40ms

the last thing i wanted to prove was that the correctness still holds when it's scaled out, so i ran three copies of the api behind an nginx load balancer all sharing the same postgres and sent about 167,000 requests through the balancer, the traffic spread evenly across all three replicas and the database came out with exactly 5,000 seats booked, 5,000 bookings and zero seats booked twice, so no oversell at all even across three separate processes, that's the whole reason the lock lives in postgres and not in the app's memory, you can run as many copies of the app as you want and the guarantee still holds because the database is the single source of truth
